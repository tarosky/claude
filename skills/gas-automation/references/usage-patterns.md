# 利用形態の3択 — 置き場所・落とし穴・対策

GASの自動化は「誰が、いくつ使うか」で**置き場所と壊れ方**が変わる。
作る本人はこの観点を持っていないことが多いので、**必ず質問し、選ばれた型の落とし穴を作る前に伝える**こと。

## 判定の質問

> このツールは誰が使いますか？
>
> 1. **自分だけ** — 自分の作業を楽にしたい
> 2. **みんなが、それぞれ自分用に使う** — 同じ仕組みを各自が自分のデータで使う
> 3. **みんなで、1つを一緒に使う** — チームやプロジェクトで1つのシートを共有する

迷っている場合は具体例で聞き分ける：

| 型 | 具体例 | 見分け方 |
|---|---|---|
| ① 自分だけ | 自分の作業ログ集計、自分宛てメールの整理 | 他の人に渡す予定がない |
| ② n人がn個 | Backlogの「自分の」課題棚卸し、自分の勤怠メモ | 中身（データ・APIキー）が人ごとに違う |
| ③ n人が1個 | 「プロジェクトA」の課題振り分け、チームの問い合わせ一覧 | データが1つで、みんなが同じものを見る |

## ① 自分だけ

- **置き場所**：自分のマイドライブ
- **実行アカウント**：自分
- **落とし穴**：ほぼ無い。ただし「便利だから共有して」と言われた瞬間に②か③に変わる。そのときはこのスキルで作り直しを検討する
- **README に書くこと**：何をするか、止め方

## ② n人がn個（原本を配り、各自がコピー）

- **置き場所**：原本は**共有ドライブ**（作った人がいなくなっても原本が残る）。各自はコピーして自分のマイドライブで使う
- **実行アカウント**：各自（トリガーはコピーされない。コピーした人がそれぞれ張る）
- **APIキー**：各自が自分のキーを入れる。**シートのメニューから入力できるようにし、User Properties に保存する**（`secrets.md`）。コピーした人にエディタを開かせない

### 標準の作り：シートにメニューを付ける

コピーした全員がエディタを開いて設定するのは、ノーコーダーには大きな負担で、ここで脱落する。②では `onOpen` でシートにメニューを付け、次をメニューから実行できるようにする（`triggers.md` の雛形）：

- 初期設定（APIキーの入力）
- 今すぐ実行
- 自動実行オン（`setup()`）／オフ（`teardown()`）

初回だけ権限の承認画面（「安全ではないページ」の警告）が**コピーした全員に**出る。README と説明タブに「自分のアカウントで動かすための確認なので許可してよい」と書いておく。

### 原本を汚さない

作った人が動作確認に使うのは**自分用のコピー**。原本には、キー・トリガー・出力データを入れない。

1. 原本を作る（共有ドライブ）
2. 原本から自分用コピーを作り、そこでキー入力・実行・自動実行オンを試す
3. 直すときは**原本のコードを直し**、自分用コピーは作り直して確認する
4. 配布は「コピーを作成」用のURLで行う：`https://docs.google.com/spreadsheets/d/<原本のID>/copy`

### 落とし穴：コピーした瞬間に別物になり、修正が届かない

原本のバグを直しても、配ったコピーには反映されない。**作る前に本人に伝え、次のどちらかを選んでもらう：**

| 方針 | やり方 | 向いている場合 |
|---|---|---|
| **割り切り（標準）** | コピーで配る。修正したら「新しい版をコピーし直して」と告知する。データは各自が新しいコピーへ移す | ほとんどの場合。機能が小さい、データが溜まらない・移しやすい |
| **ライブラリ化（上級）** | 処理本体を別のGASプロジェクト（ライブラリ）に置き、コピー側は呼び出すだけにする | データの移し替えが重く、今後も機能を足し続ける。**clasp モード必須**、作った人がコードを管理し続けられる場合のみ |

ライブラリ化しても「何もしなくても全員に修正が届く」わけではない。安定した版を参照させる限り、更新のたびに各自が参照する版を上げる作業が要る（減るのはコピーし直しとデータ移行だけ）。それを理解したうえで選んでもらう。

### ライブラリ化する場合の注意（公式仕様）

- ライブラリ本体も共有ドライブに置き、利用者全員に**閲覧権限**を付ける
- 公開は「デプロイ → 新しいデプロイ → 種類：ライブラリ」（clasp なら `create-version`）。利用者は**版を指定**して参照する。HEAD（開発モード）は**編集権限のある人にしか効かない**
- **ライブラリの中で Script Properties を読まない**。ライブラリ内で作った Script Properties は全利用者で同じものになる。キーはコピー側で読んで、引数でライブラリの関数に渡す
- **トリガー・メニュー（`onOpen`, `main`, `setup`, `teardown`）はコピー側に置く**。ライブラリの関数はトリガーから直接呼べないので、コピー側に中継の関数を書く
- clasp では `library/` と `sheet/` にプロジェクトを分け、それぞれに `.clasp.json` を置く。コピー側の `appsscript.json` に参照を書く：

```json
{
  "timeZone": "Asia/Tokyo",
  "runtimeVersion": "V8",
  "dependencies": {
    "libraries": [{ "userSymbol": "Lib", "libraryId": "<ライブラリのスクリプトID>", "version": "1" }]
  }
}
```

- **README と説明タブに書くこと**：原本のURL、コピー用URL、初回の手順（メニュー → 初期設定 → 自動実行オン）、承認画面の説明、更新があったときの手順

## ③ n人が1個（共有ドライブで1つを使う）

- **置き場所**：**共有ドライブ**（必須）。マイドライブに置くと、作った人の退職・異動でファイルごと消える・引き継げなくなる
  - Googleフォームを使う場合は、**フォーム本体も**共有ドライブに置く。シートだけ移してもフォームが作成者のマイドライブに残る
  - 後から移動しようとすると、共有ドライブの権限（投稿者では移動できないことがある）や組織のポリシーで止まることがある。**最初から共有ドライブの中で作る**のが安全
- **実行アカウント**：トリガーを**設定した人**

### 落とし穴：作った人のアカウントで動いている

インストール型トリガーは「設定した人のアカウント」で動く（Google公式仕様）。ファイルを共有ドライブに置いても、これは変わらない。つまり：

- 設定した人が退職・アカウント停止・権限を失うと、**誰にも通知されずに止まる**
- 外部サービスのAPIキー（Backlog・Slack等）も、たいてい誰か個人のキー。その人がいなくなると止まる
- メール送信はその人の名前で送られ、その人の送信上限を消費する
- Gmail を読む処理なら、読めるのは**その人の受信箱だけ**
- エラーの通知メールは**トリガーを張った人にしか届かない**。他のメンバーは止まったことに気づけない

**作る前に、次の2つを人名で確定させる：**

1. **運用オーナー**：トリガーを設定し、止まったら気づいて直す人
2. **APIキーの持ち主**：外部サービスのキーを発行した人（可能なら個人ではなく、チーム用・サービス用アカウントのキーにする）

作った人と運用オーナーが別人の場合、**作った人は動作確認が終わったら自分で `teardown()` を実行してから引き渡す**。`teardown()` で消せるのは自分が張ったトリガーだけなので、両方が `setup()` すると2本動いて通知が二重になる。

オーナーが変わるときの引き継ぎ手順（旧オーナーが `teardown()` → 新オーナーがエディタを開いて承認し `setup()` → キーを差し替え）をREADMEに書いておく。

- **README に書くこと**：運用オーナー、APIキーの持ち主、引き継ぎ手順、止め方。フォーム起点なら「質問の文言を変えると処理が壊れる」こと

## 型が決まったら

選ばれた型と、伝えた落とし穴、決めたこと（②の方針、③のオーナー・キー保有者）を1〜3行でまとめて本人に確認し、README の冒頭にもそのまま残す。
