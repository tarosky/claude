# デモデータの戦略

Live Preview の価値は、デモデータで決まる。シナリオ（`demo-design.md`）を決めたら、データの**作り方**をここで決める。

## 4 つの軸で分類する

| 軸 | 問い | 影響 |
|---|---|---|
| 量 | 一覧・検索・ページネーション・関連記事・集計など、件数が無いと見せ場にならないか | 生成方式と待ち時間 |
| 時間 | 予約公開・期限切れ・イベント・「営業中」・「◯日前」など、現在時刻に依存するか | **必ず実行時の時刻から相対で作る**。固定日付は数か月後に壊れる |
| メディア | 画像・ファイルが必要か | 取得元と容量。`features.networking` |
| 外部依存 | API キー・AI サービス・メール・決済・外部 API が必要か | Playground では動かない。見せられるかを先に判定する |

時間の軸は量が少なくても該当する。気づかずに固定日付で書くと、公開から数か月後に「期限切れのデモ」が出ても誰も気づかない。

## 外部依存のある機能は見せられない

Playground には API キーも無く、メールも送れない。プラグインの売りがそこにある場合は、ヒアリングの最初に伝えて、代わりに何を見せるかを決める。

- 例: hamelp の売りは AI Overview だが、AI サービスの設定が必要なので Live Preview では動かない。FAQ の投稿タイプ・カテゴリ・インクリメンタル検索を見せ、AI Overview は README の外部デモへ誘導する
- API キーをデモ用に blueprint に入れない（blueprint は公開ファイル）

## 作り方の選択肢

| 方式 | 向いているケース | 代償 |
|---|---|---|
| A. demo.php に直接書く | 少量（〜20 件）・静的 | 量が増えると読めない |
| B. demo.php でループ生成 | 中量（〜200 件）、時刻から相対で作るデータ | プラグイン内部の API が変わると壊れる（他の方式も同じ） |
| C. プラグインにデモ生成の関数・WP-CLI コマンドを同梱し、blueprint からは呼ぶだけ | 量が多い、構造が複雑、同じデータを開発・テストでも使いたい | 配布物にデモ用コードが入る。API 変更への追従はプラグインのテストで担保できる |
| D. WXR を `importWxr` で読み込む（GitHub の raw URL など） | 画像付きの大量の投稿 | 外部 URL に依存。カスタムテーブル・一部のメタは入らない |

迷ったら B から始める。C は「開発用のシーダーとしても欲しいか」をユーザーに聞いてから選ぶ（プラグイン本体の変更になるので、blueprint の PR とは分ける）。

D とスナップショット（`importWordPressFiles`）は、このスキルではまだ検証していない。選ぶ場合は `verify.sh` で必ず実測する。

## 生成のコツ（B・C）

- **乱数のシードを固定する**（`mt_srand( 固定値 )`）。プレビューのたびに見た目が変わらず、スクリーンショットや説明と食い違わない
- **lorem ipsum を使わない。** 検索などの見せ場では、本物らしい文が要る。「カテゴリ × 対象 × 質問のテンプレート」のように組み合わせると、少ない記述で数十件の自然な文を作れる（hamelp の例）
- **日付は `time()` からの相対で作る**（`time() - mt_rand( 1, 90 ) * DAY_IN_SECONDS` など）。未来の予定・期限も同様
- **まとめて入れるときは高速化する**:

```php
global $wpdb;
wp_defer_term_counting( true );
$wpdb->query( 'START TRANSACTION' );
// ... 投入 ...
$wpdb->query( 'COMMIT' );
wp_defer_term_counting( false ); // ここで保留していた件数がまとめて更新される
```

## 実測（2026-10、@wp-playground/cli・Apple Silicon の Mac）

投稿 1 件＝`wp_insert_post` ＋メタ 1 つ＋カテゴリ 1 つ。「PHP 内」は demo.php の実行時間、「全体」は起動から blueprint 完了まで（空のデモで 10〜12 秒）。

| 件数 | 高速化なし（PHP 内 / 全体） | トランザクション＋件数更新の保留（PHP 内 / 全体） |
|---|---|---|
| 50 | 1.6 秒 / 10 秒 | — |
| 200 | 6.8 秒 / 16 秒 | 3.7 秒 / 12 秒 |
| 1000 | 31 秒 / 39 秒 | 17 秒 / 25 秒 |

- 1 件あたり約 30 ミリ秒、高速化すると約 17 ミリ秒。高速化でおよそ半分になる
- 訪問者のブラウザで動く PHP（WebAssembly）は、これより遅いと考える。**demo.php の実行時間は数秒以内**を目安にし、数百件を超えるなら件数を絞るか、方式 C を検討する
- 見せ場に必要な件数は、たいてい思ったより少ない。ページネーションなら 2〜3 ページ分、検索なら「キーワードで数件ヒットする」程度で足りる

## 落とし穴

- **runPHP はログインユーザー無しで動く。** `wp_insert_post()` の `tax_input` など、権限チェックのある処理は**エラーを出さずに無視される**（hamelp の試作でカテゴリの件数がすべて 0 になった）。雛形の先頭に `wp_set_current_user( 1 );` を入れてある。消さないこと
- **着地ページの文字列が出ても、データが正しいとは限らない。** 件数・関連付け・日付は、`KEEP_RUNNING=1` で起動したまま REST API で確かめる（`verify.sh` が作る Cookie ジャーを使う）

```bash
KEEP_RUNNING=1 bash <skill>/scripts/verify.sh . <out> "期待する文字列"
curl -sL -c <out>/cookies.txt -b <out>/cookies.txt "http://127.0.0.1:9431/wp-json/wp/v2/<rest_base>?per_page=100"
pkill -f 'wp-playground/cli.*--port=9431'
```
