# 「設定されているのに効いていない」チェックリスト

tarosky/sportivo-school の Node 24 化で実際に見つかったもの。どれも、見た目は正しく設定されていて、確認するまで気づかなかった。

作業中に一つずつ確認する。見つけたものは、Node 24 化に必要なら直し、そうでなければ Issue にする。

## ビルド

- [ ] **ビルドエラーが握りつぶされていないか**
  gulp-plumber はエラーを捕まえてログに出すだけで、タスクは成功扱いになる。sportivo-school では CI の CSS ビルドが毎回失敗していたが、終了コードは 0 で、コミット済みの `dist/` がそのまま出荷されていた。
  確認: 出力ディレクトリを消してからビルドし、全ファイルが作り直されるかを見る。

- [ ] **ビルドがリポジトリ外のファイルに依存していないか**
  子テーマの Sass が親テーマ（`../submit/assets/scss`）を読み込んでいて、CI にはそのディレクトリがなかった。ローカルと CI で出力が違う、または CI では作れない。
  確認: `detect_node.mjs` の `outside-repo-path`。CI のビルドログ。

- [ ] **リリースに入るのは、CI のビルドか、コミット済みのファイルか**
  `dist/` がコミットされていると、CI のビルドが失敗しても気づかない。どちらが正なのかを README に書く。

- [ ] **非推奨警告を消していないか**
  `quietDeps` / `silenceDeprecations` で約 1,000 件の Sass 警告が見えなくなっていた。警告は消さず、対応は Issue にする。

## lint・テスト

- [ ] **lint がエラーで終了コード 1 を返すか**
  `npm run lint` が 59 件のエラーを出して終了コード 0 で終わっていた（gulp タスクがエラーを返していなかった）。
  確認: `npm run lint; echo $?`

- [ ] **lint・テストが CI で実際に動いているか**
  `package.json` に lint があっても、workflow から呼ばれていないことがある。ジョブがコメントアウトされていることもある。

## CI

- [ ] **サービスコンテナが実際に使われているか**
  workflow に MySQL 5.7 のサービスがあったが、テストは別の手順で起動した MySQL を使っていて、サービスは使われていなかった。
  確認: テストの接続先（ホスト・ポート）がサービスを指しているか。

- [ ] **ほかの失敗に隠れた失敗がないか**
  PHP バージョン指定の typo（`8.3'`）で CI が壊れていたが、ほかのジョブの失敗に埋もれていた。一つ直すと次の失敗が見えることがある。

## 設定ファイル

- [ ] **設定名が古くなっていないか**
  WordPress Coding Standards 3 で `minimum_supported_wp_version` が `minimum_wp_version` に変わり、古い名前は黙って無視されていた。
  確認: 設定値を変えて、結果が変わるかを試す。

- [ ] **設定が効くための前提が揃っているか**
  phpcs ルールセットの `testVersion`（PHP の対応バージョン）は、PHPCompatibility が入っていないと何も確認しない。

## 確認の基本

設定ファイルを読んで「設定されている」と判断しない。**わざと違反する入力を入れて、結果が変わるかを試す。** 変わらなければ効いていない。
