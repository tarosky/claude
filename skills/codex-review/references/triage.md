# 指摘のトリアージと評価の記録

## 判定の基準

指摘は 1 件ずつ、**コードを読んで根拠を確かめてから**判定する。Codex の説明文だけで判断しない。

| 判定 | 条件 | 根拠に書くこと |
|---|---|---|
| 採用 | 指摘されたシナリオが実際に起きることを、コード・テスト・実行で確かめた | 発生する経路（ファイル:行、入力・状態） |
| 却下 | 起きないことを確かめた、または仕様どおりの挙動である | 起きない理由（ガードしている箇所、呼ばれない経路、仕様の出典） |
| 要確認 | 仕様の判断が要る、確かめる手段が無い、修正の範囲が依頼を超える | 何が分かれば判定できるか、誰に聞くか |

### 偏りを避ける

- **鵜呑みにしない**: Codex は差分の周辺しか読まないことがある。呼び出し元で弾かれている・別の場所で処理済みなどの誤検知は多い
- **かばわない**: 自分（Claude）が書いたコードへの指摘ほど、却下に傾きやすい。「意図どおり」で却下するときは、意図の出典（Issue・プラン・ユーザーの指示）を示す。出典が無ければ要確認にする
- **重大度で判定を変えない**: P1 でも誤検知なら却下、P3 でも本物なら採用（直すかどうかは別に決めてよい）
- 確かめるのにテストやコマンドの実行が要るなら、実行してよい（Codex と違い、Claude は書き込める。ただし検証用のファイルはスクラッチパッドに置く）

### 仕様への懸念

「仕様どおりだが危うい」という指摘は、バグとして採用も却下もせず**要確認**にし、ユーザーに判断を仰ぐ。

## 修正

- 採用した指摘だけを直す。要確認はユーザーの判断を待つ
- 直したら、通常どおりテスト・lint を実行する
- **Codex に再レビューさせない。** 往復は 1 回で打ち切る。修正が大きく、どうしても見てほしい場合は、ユーザーに確認してから別の範囲（`--commit <修正のSHA>`）として 1 回だけ実行する

## ユーザーへの報告

```
Codex レビュー: 指摘 N 件 → 採用 A / 却下 R / 要確認 Q（所要 M 秒）

| # | 重大度 | 指摘（要約） | 判定 | 根拠 |
|---|---|---|---|---|
| 1 | P1 | init で出力している | 採用 | plugin.php:11。REST でも JSON の前に出力される。修正済み |
| 2 | P2 | 毎リクエストで option を消す | 却下 | 仕様（#12 の要件）。意図として Codex に渡していた |
```

要確認があれば、表のあとに「判断してほしいこと」として箇条書きで並べる。

## 評価の記録

このスキルは「Codex を GitHub Actions のレビュアーに加える価値があるか」を見極める段階にある。PR を作るときは、本文の末尾に次の節を入れる（PR に残しておけば、GHA の `claude-review` のコメントと同じ場所で突き合わせられる）。

```markdown
## Codex レビュー記録

- 範囲: `--base main`（コミット 3 件）、プリセット: wordpress、所要 95 秒、codex-cli 0.167.0
- 指摘 3 件 → 採用 1 / 却下 1 / 要確認 1

| # | 重大度 | 指摘 | 判定 | 根拠 |
|---|---|---|---|---|
| 1 | P1 | ... | 採用 | ... |

<!-- claude-review の結果が出たら追記: Codex のみが拾った本物の指摘 = #1 -->
```

- 指摘の本文は要約でよい。顧客名・未公開の情報は書かない（公開リポジトリの場合）
- `claude-review` の結果が出たら、「Codex だけが拾った採用の指摘」の番号を HTML コメントに書き足す。両方が拾ったもの、`claude-review` だけが拾ったものも分かれば書く
- 集計は `gh search prs "Codex レビュー記録" --owner tarosky` で PR を集めて行う。数本やって「Codex だけが拾った本物の指摘」がほとんど無ければ、GHA への展開は見送る
